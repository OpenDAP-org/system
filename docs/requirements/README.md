# System requirements

Requirements for Blackbird OS system software. Most of these record the intent from the project brief; the software stack is not defined yet.

| ID | Requirement | Priority | Status |
|---|---|---|---|
| SYS-001 | Developers shall extend the system with **capabilities** (business logic, user-space drivers, …) instead of standalone apps. | must | Draft |
| SYS-002 | Each capability shall declare in a manifest what it needs and what it provides. | must | Draft |
| SYS-003 | Services shall follow the Unix philosophy. They may be ephemeral (CLI-like) or persistent (engines), and run in the foreground or as background tasks. | must | Draft |
| SYS-004 | Services shall talk over a bus with a standardized API. | must | Draft |
| SYS-005 | Data schemas and UI components shall be versioned and published in a signed, versioned index. | must | Draft |
| SYS-006 | The UI shall show **activities** instead of windows. Activities pause, resume and are destroyed on demand as they enter or leave the foreground. | must | Draft |
| SYS-007 | Capabilities shall be able to add tasks to existing activities. Example: on the now-playing activity, one service adds a "like" action and another adds a lyrics tab. | must | Draft |
| SYS-008 | The UI runtime shall support dynamic two-way data binding. | must | Draft |
| SYS-009 | All UI shall follow the official design system. | must | Draft |
| SYS-010 | There shall be no app store. Packages are fetched over HTTP using a reverse-domain / well-known scheme. | must | Draft |
| SYS-011 | Package downloads shall always go through the package endpoint configured in the image, and the device shall verify signed, expiring metadata and honour signed recalls. | must | Draft |
| SYS-012 | Hearing safety (required for personal music players; compliance requirement): a local weekly sound-dose budget over a rolling seven days, with an 85 dB(A) limit and per-headphone profiles (EN 50332). | must | Draft |
| SYS-013 | When a HAT is connected, the UI shall show that it is verified, its signature status, power draw, permissions and where its capabilities appear. | must | Withdrawn |
| SYS-014 | Errors shall be explained in a human sentence with the next step, never blaming the user. | must | Withdrawn |
| SYS-015 | Button behavior: Action ×1/×2/×3 = play-pause / next / previous; holding Action captures an idea; Volume − always lowers the volume. | should | Withdrawn |
| SYS-016 | Activities instead of icons: Listen, Watch, Read, Create and Day, plus Advanced. | should | Withdrawn |
| SYS-017 | The UI shall not look or behave like an operating system (no launcher, app grid or app icons): it shall feel like the dedicated, purpose-specific interface of a consumer electronic product. | must | Confirmed |
| SYS-018 | Dynamic UI components are key: capabilities and HATs shall be able to bring versioned UI components from the registry at runtime, without rebuilding the shell, within the design system. | must | Confirmed |
| SYS-019 | Developers shall create services, UI components, data schemas and bindings in a simplified way, in Rust, through the official SDK. | must | Confirmed |
| SYS-020 | Using the SDK shall enforce the project's optimizations, practices and patterns. | must | Confirmed |
| SYS-021 | The UI shall provide its own on-screen keyboard, designed for the T1's display and interaction, as part of the product UI system. | must | Confirmed |
| SYS-022 | Third parties shall be able to provide custom keyboards, installed and selected like other capabilities. | must | Confirmed |
| SYS-023 | The default keyboard shall be a mini QWERTY layout. | must | Confirmed |
| SYS-024 | The keyboard shall offer contextual variants chosen by the field it serves (for example text, search, email, URL, number, phone, PIN and password) and by the activity's context. | must | Confirmed |
| SYS-025 | The whole UI shall be i18n-first: every user-facing string, format and layout is localizable from the start, with locale-aware dates, numbers, units and plural rules, right-to-left layouts, and fonts for the supported scripts. This applies to the system, the templates and capabilities built with the SDK. | must | Confirmed |
| SYS-026 | The keyboard shall be i18n-first too: layouts per language, input methods that compose text (for example Chinese, Japanese and Korean), and switching between the user's languages; third-party keyboards can add languages. | must | Confirmed |
| SYS-027 | The default language shall be English. | must | Confirmed |
| SYS-028 | The UI and the keyboard shall ship with the five most spoken languages in the world, by total speakers: English, Mandarin Chinese, Hindi, Spanish and Arabic. | must | Confirmed |
| SYS-029 | Language data (translations, keyboard dictionaries and prediction models) shall be optimised for progressive loading: a small core first, the rest loaded on demand. | must | Confirmed |
| SYS-030 | There shall be one official theme. The UI architecture shall still support community themes from the start (themes as design-system token sets and template-based layouts), because an open platform will attract them. | must | Confirmed |
| SYS-031 | Installing software from outside the package endpoint shall be possible in developer mode, and developer mode shall be simple to turn on. | must | Confirmed |
| SYS-032 | Permissions shall eventually be capability-based and granular; until that system exists, capabilities shall simply work, and the missing permission system shall never block them. | must | Confirmed |
| SYS-033 | Every service and UI component shall work in bounded memory and time regardless of data size: indexed queries, paginated and incremental loading, virtualised lists, streaming instead of loading whole collections, and no O(n) work on the UI thread. | must | Confirmed |
| SYS-034 | Every service shall run indefinitely without degradation: no memory or file-descriptor leaks, bounded caches and logs, and resource use exposed so tests and users can see it. | must | Confirmed |
| SYS-035 | OpenDAP builds and supports its own software ecosystem: the OS, SDK, UI, services and first-party capabilities. Third-party apps, alternative shells and custom distributions are the community's scope: the architecture shall allow them (documented image build, separable board support, owner-controlled boot), but OpenDAP does not support them. | must | Confirmed |
| SYS-036 | The UI shall never wait on work: the render and input path has priority over every background task, no blocking call runs on the UI thread, and background work (indexing, artwork, network, updates) is scheduled so it can never take frames from the UI or samples from audio. | must | Confirmed |
| SYS-037 | Large audio buffers used to save power shall never delay a user action: volume is applied in the DAC immediately, and play, pause, seek and track changes flush or bypass the buffer instead of waiting for it to drain. | must | Confirmed |
| SYS-038 | The status bar at the top of the screen should show, at the start: the time, the microSD card status and a speaker icon with the volume level, in that order; and at the end: the Bluetooth status, the Wi-Fi status, the battery percentage and the battery icon, in that order. The volume indicator uses the semantic colours to show whether the level is within the safe-listening limit or in the warning range (SYS-012). | should | Confirmed |
| SYS-039 | The touch UI should support gesture navigation: from the leading edge, back; from the trailing edge, the screen's companion screen (from Now Playing, the queue); from the bottom, more of the current screen; from the status bar, notifications and quick settings. Draggable controls near an edge exclude their area from the edge gestures, and every gesture has a visible single-tap alternative. | should | Confirmed |
| SYS-040 | Blackbird OS and OpenDAP software shall not be tied to one hardware design: they detect what the hardware can do and adapt to it automatically. Hardware limits never limit the software's capabilities: a capability the hardware lacks is disabled in software, not left out of it. | must | Confirmed |
| SYS-041 | Audio UX runs on one axis, from the audiophile (enjoying music with sparkle and high quality, for listening) to the engineer (monitoring, analysing, comparing, finding the smallest detail). Defaults always serve the audiophile; every engineering capability stays one step away, never hard to reach. | must | Confirmed |
| SYS-042 | Playback shall be synchronised in real time across all of the listener's devices: what is playing, its position, the queue and the playback state are the same on every device, and any device can take over playback where another left it. | must | Confirmed |
| SYS-043 | OpenDAP shall support a shared household: one shared music collection, with each member's personal state (playlists, ratings, history, audio profiles, device selections) kept apart. | must | Confirmed |
| SYS-044 | A household should have family members, in the manner of streaming services' profiles: the owner adds members, each with their own personal state, and a shared device can switch between them. | should | Confirmed |
| SYS-045 | Every third-party service (metadata such as MusicBrainz and AcoustID, stores, streaming, scrobbling and any other) shall be integrated as a provider: optional, opt-in and never part of the core. | must | Confirmed |
| SYS-046 | Several of the listener's devices should be able to play the same music at the same time, in sync (multi-room). | should | Confirmed |
| SYS-047 | Everything OpenDAP offers shall work without an account or a signed-in session of any kind. Accounts, and every feature that depends on one, are opt-in. | must | Confirmed |
| SYS-048 | Everything the listener sees (folders, file and playlist formats, exports, pairing, sync status, deletion and undo, updates) shall use formats, standards and conventions people already know. Internal formats may differ, and no listener who is not a developer ever needs to know them. | must | Confirmed |
| SYS-049 | The listener's collection shall never change without their action: tag edits, renames, moves, deduplication and conversions are previewed and applied only on request, every batch can be undone, and sync never deletes, replaces or converts an original as a side effect. | must | Confirmed |
| SYS-050 | Deleting music or playlists shall be recoverable: deleted items stay in Recently Deleted for 30 days on every device; destructive device actions (erase, reset, remove all music) are confirmed on the device itself, never only over the network. | must | Confirmed |
| SYS-051 | Sync, transfer and pairing shall show their state the same way on every surface (synced, syncing, waiting, paused, can't sync with the reason), with what is on which device one step away. | must | Confirmed |
| SYS-052 | Changes made on several devices, even offline, shall never be lost: they merge where the intent is clear; otherwise both versions are kept and the conflict is shown once. | must | Confirmed |
| SYS-053 | Plays and skips shall be recorded as events with the time they happened and merged across devices without losing that time. | must | Confirmed |
| SYS-054 | Everything the listener owns or creates (playlists, history, ratings, audio profiles, settings, backups) shall export in documented, widely used formats from every surface and re-import without loss. | must | Confirmed |
| SYS-055 | Privacy by default: listening data stays on the listener's devices; any network use is opt-in and listed with its endpoint; nothing is reachable from the internet by default. | must | Confirmed |
| SYS-056 | A device's identity shall be its key, recorded at pairing; every control and data endpoint requires a paired key; links (Wi-Fi, Bluetooth, USB networking) are protected by authenticated encryption at the application layer; there are no default credentials, and file and remote services are off until enabled. | must | Confirmed |
| SYS-057 | No vendor, store or provider shall be able to delete or disable the listener's content remotely, and nothing acquired depends on a server to play. | must | Confirmed |
| SYS-058 | No function of the T1, OpenDAP Desktop or the CLI shall depend on an online service to keep working: online services add reach and capacity, never a capability. | must | Confirmed |
| SYS-059 | No surface shall use dark patterns (nagging, obstruction, sneaking, interface interference, forced action), and no provider is placed or ranked by commercial arrangement. | must | Confirmed |
| SYS-060 | A redesign or rewrite of any user-facing surface shall ship only at parity with a written list of the features it replaces; an accessibility regression blocks the release. | must | Confirmed |
| SYS-061 | The interface shall meet WCAG 2.2 AA as WCAG2ICT applies it to non-web software and EN 301 549, with AT-SPI semantics (role, name, state, value, actions) for every element and accessible documentation, whether or not a law requires it. | must | Confirmed |
| SYS-062 | Blackbird OS shall provide built-in voice guidance, operable from the buttons and by touch, that can be turned on without sight at first run and at any time. | must | Confirmed |
| SYS-063 | Text size shall be adjustable in steps up to about 200 % with layouts that reflow, plus a large-text mode with an x-height of at least 2.38 mm (EN 301 549 V4.1.1 5.1.4). | must | Confirmed |
| SYS-064 | Display options shall include increased contrast, bold text, reduced motion, transparency and effects; a light, high-contrast appearance and colour filters should also be offered. | must | Confirmed |
| SYS-065 | Audio accessibility shall include mono and left/right balance, bit-transparent when off; hearing-aid support (LE Audio hearing access, ASHA) should be offered where the radio supports it. | must | Confirmed |
| SYS-066 | Press, hold and repeat timings of the buttons and the touch screen shall be adjustable. | must | Confirmed |

## Open questions

- SYS-038: whether the microSD, Bluetooth and Wi-Fi indicators are always shown or only when a card is inserted or the radio is on.
- SYS-038: the unit of the volume level (steps, percent or dB) and where the safe and warning thresholds sit, which depend on SYS-012 and the headphone profile.

## Context

- SYS-061 to SYS-066 (2026-10-23): decided under the maintainers' delegation from the [small-screen interface and accessibility research](https://github.com/opendap-project/t1/blob/main/docs/research/ux/2026-10-small-screen-ui-accessibility.md) §8. Linux has no touch screen reader (GNOME Orca issue 207), so voice guidance is OpenDAP's own, built on AT-SPI. The light appearance and colour filters are the should parts of SYS-064; hearing aids the should part of SYS-065.
- SYS-049 to SYS-060 (2026-10-23): confirmed under the maintainers' delegation, after they asked Claude to resolve the pending points with the project's design philosophy.
- SYS-049 to SYS-060 (2026-10-23): proposed by Claude from the principles of the [ecosystem experience research](https://github.com/opendap-project/t1/blob/main/docs/research/ux/2026-10-ecosystem-experience.md) (E5 to E9, E17, E18) and the lessons of the [case studies](https://github.com/opendap-project/t1/blob/main/docs/research/ux/2026-10-ecosystem-case-studies.md) (iCloud Music Library 2016, Kindle 2009, PlaysForSure, KDE Connect CVE-2025-66270, My Book Live 2021, Sonos 2024, Car Thing 2024). Draft until the maintainers confirm them. The user-facing forms are in the [conventions spec](../specs/user-facing-conventions.md).
- SYS-048 (maintainers, 2026-10-23): every user-facing choice cites the convention it follows; internal representations are documented separately for developers.
- SYS-047 (maintainers, 2026-10-23): no account is ever required. Pairing, sync between the owner's devices, the shared household (SYS-043) and every core feature work without one; features that need an account (for example family members, SYS-044) are opt-in, like every third-party provider (SYS-045).
- SYS-044 (maintainers, 2026-10-23): a should, because members need an identity of their own across devices, which is opt-in (SYS-047); the shared household itself (SYS-043) is a must and works without it.
- SYS-046 (maintainers, 2026-10-23): multi-room is a should, separate from the real-time playback sync of SYS-042, which is a must. Open precedents: Sendspin and Snapcast ([protocol research](../research/2026-10-device-ecosystem-protocol.md) §4).
- SYS-042 to SYS-045 (maintainers, 2026-10-23), from the [ecosystem experience research](https://github.com/opendap-project/t1/blob/main/docs/research/ux/2026-10-ecosystem-experience.md) §13.1 and the [protocol research](../research/2026-10-device-ecosystem-protocol.md). SYS-042: people value playback continuing across all their devices in real time; it is a must. Simultaneous, sample-synchronised playback on several devices (multi-room) is a different feature and is not recorded here. SYS-045: third parties can all be integrated, but always as opt-in providers; the core works with none of them.
- SYS-040 (maintainers, 2026-10-23): the software is written for capabilities, not for one board; it turns on what the hardware it runs on provides, and the rest stays in the code, disabled. It complements T1-045 (software never limits the hardware) from the other side (hardware never limits the software).
- SYS-041 (maintainers, 2026-10-23): the rule of audio UX. Applied first in the [audio profiles spec](https://github.com/opendap-project/t1/blob/main/docs/specs/audio-profiles.md).
- SYS-039 (maintainers, 2026-10-23): the T1 has no phone-style home, so the bottom swipe opens more of the screen, as streaming players do. Research: [buttons, gestures and touch on a small screen](https://github.com/opendap-project/t1/blob/main/docs/research/ux/2026-10-controls-gestures-small-screen.md).
- SYS-038 (maintainers, 2026-10-23): a volume indicator (speaker icon and level) joins the start of the bar after the microSD status, coloured by the semantic colours for safe and warning.
- SYS-035 (maintainers, 2026-10-22): the default experience is OpenDAP's own ecosystem; everything third-party stays out of it. The rule "100 % of the hardware, never software limits" (T1-045) still applies to OpenDAP's own software.
- SYS-030 to SYS-032 and SYS-012 (maintainers, 2026-10-22, after the [community research](https://github.com/opendap-project/t1/blob/main/docs/research/ux/2026-10-community-mods-customisation.md)): hearing safety is important. The limits required by law (EN 50332) are fixed and always visible to the user; everything beyond them is adjustable (T1-045).
- SYS-028 language list (maintainers, 2026-10-22): English, Mandarin Chinese, Hindi, Spanish and Arabic. Arabic makes right-to-left layout (SYS-025) a launch requirement: Slint does not mirror layouts yet (issue #2294), so OpenDAP provides mirroring in its own generator, and upstreams it without waiting for acceptance (patched Slint in its own packages meanwhile, OS-023). Language data licensing: [ADR 0007](../adr/0007-language-data-licensing.md).
- SYS-024 to SYS-026 (2026-10-22), proposed direction, to be researched: the field's purpose and hints travel through `text-input-v3` (content purpose and hints), so the keyboard picks its variant without app code. Locale data from Unicode CLDR; formatting, plural rules and text segmentation through ICU4X (the Unicode Consortium's Rust implementation); message translation through Slint's built-in translation support or Project Fluent. Every choice here is **UNVERIFIED** until the research is done.
- SYS-021 to SYS-023 (2026-10-22), proposed direction, to be researched: the keyboard is an input method on the standard Wayland protocols (`zwp_input_method_v2` on the compositor side, `text-input-v3` in apps; Smithay and Slint support is **UNVERIFIED**), so every activity gets text entry without its own keyboard. Third-party keyboards are capabilities with a privileged `input.method` permission, because a keyboard sees everything typed; password and other sensitive fields always use the system keyboard, as on Android and iOS. Faceplates without touch (cassette, classic) need a non-touch text entry method on the same input-method interface (for example a character wheel driven by HID controls).
Direction from the project brief, not specified yet: a custom orchestrator coordinates services; the bus is Rust-native and high-performance, more modern than CBOR; the UI runtime is opinionated, reactive and based on Slint, running on Wayland.

- SYS-012 to SYS-016: Adopted from the earlier experiments on 2026-10-21 as **Draft**: consistent with the decisions already taken and with the product philosophy, pending the maintainers' confirmation. Part availability still has to be checked against the sourcing rule (T1-010).
- Withdrawn on 2026-10-21 after the [experiment review](https://github.com/opendap-project/t1/blob/main/docs/research/2026-10-experiment-review.md): SYS-015, SYS-016.
- Withdrawn on 2026-10-21: SYS-013 and SYS-014 came from the earlier UI prototype, which is discarded entirely together with its design system. SYS-012 stays because EN 50332 requires it, not because of the prototype.
- The SDK plays the role the Android SDK plays for Kotlin/Java, or SwiftUI and Apple's frameworks for Swift: Rust is the language; the OpenDAP SDK is the platform layer (services, schemas, bindings) and the declarative UI framework (components) that developers build with.
